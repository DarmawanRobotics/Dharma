\chapter{Health and diagnostics}
\label{ch:health}

\pkg{dharma_health} watches the stack and the computer. Its single node,
\code{health_monitor_node}, runs every check each \param{period_sec} (1~s) and publishes a typed
\topic{health/status} (\code{HealthStatus}, latched: \code{level} OK / WARN / ERROR, \code{issues}
with one line per problem, errors first, and \code{speed_scale} in $[0, 1]$) and a
\topic{diagnostics} array with one \code{DiagnosticStatus} per checked item, named
\texttt{health: <item>}, for \code{rqt_robot_monitor}. It reads the shared \param{robot.*} profile
for the frames of the odometry chain.

\section{Checks}

Every check family is a \code{Check} class in \code{core/checks/} that returns one finding per
item, OK included, so a diagnostic never disappears when it recovers.

\begin{description}
  \item[Sensors] (\code{sensor:<topic>}). Each entry of \param{sensors.topics} is
    \code{topic:min_hz[:max_age_sec]}. The topics are subscribed \emph{raw}: the header stamp is
    read from the serialized CDR bytes (both byte orders), so a point cloud is never
    deserialized. The rate over \param{sensors.window_sec} is
    $\hat f = (N - 1)/(t_N - t_1)$ (\code{dharma_utils.math.RateMeter}); a topic is silent
    ($\hat f = 0$) when $t - t_N > \max(1, 3/\hat f)$ and slow when
    $\hat f < $ \param{rate_tolerance}${}\cdot f_{\min}$ (0.8). The stamp age matters as much as
    the rate: a 10~Hz topic with stamps 2~s in the past passed the 0.1 checks and is now late.
    A stamp more than \param{max_future_sec} ahead of the clock is reported as a clock offset. A
    topic that is not published, or whose type is not installed, warns with the reason.
  \item[TF] (\code{tf:<parent>-><child>}). The ages of every dynamic edge
    (\code{TfCache.edge_ages}) are kept over \param{tf.window_sec} and classified
    (\code{core/checks/tf.py}): a fresh edge is OK; a stamp more than \param{tf.max_future_sec}
    ahead is a clock offset (\texttt{cause: clock}); a late edge whose stamp stopped advancing is a
    stopped publisher (\code{stopped}); late ages that stay within \param{offset_jitter_sec} of
    each other are a steady source clock offset (\code{clock}), e.g.\
    ``\texttt{camera\_init->body 1.8 s old, steady (source clock offset?)}''; late ages that vary are
    late delivery (\code{load}). Edges listed in \param{tf.edges} must exist; an edge that
    disappears is reported as gone. The robot's \frm{odom}$\to$\frm{base_link} chain gets its own
    finding.
  \item[Clock] (\code{clock:ntp}, off by default). With \param{clock.enabled} the node runs
    \texttt{chronyc tracking} every \param{clock.period_sec} and warns when the reported offset
    exceeds \param{clock.max_offset_sec} (50~ms), when the clock is not synchronized or when the
    command fails or times out.
  \item[State] (\code{state:*}). The typed statuses: odometry \code{LOST} is an error,
    \code{INITIALIZING} and \code{DEGRADED} warn; localization \code{NONE} and
    \code{UNCERTAIN} warn (review \#9: 0.1 reported OK while the robot was not localized);
    control errors on an engaged e-stop (with its reasons) and on a \code{STALE} or \code{BLIND}
    protective field. A status that never arrived or is older than \param{state.timeout_sec}
    warns. The 360° safety scan is an error when it is older than \param{scan_timeout_sec} or
    blind (every sector \code{BLOCKED} or NaN) and a warning when some sectors are blocked; a
    scan that never arrived warns during \param{startup_grace_sec} and is an error afterwards.
    An empty topic parameter turns its check off.
  \item[Nodes] (\code{node:<name>}). Every \param{nodes.expected} entry is a fully qualified
    name \code{/namespace/name}, compared with the running nodes including their namespaces
    (review \#13). Missing nodes warn during the start-up grace and are errors afterwards; a node
    running twice warns.
  \item[System] (\code{system:*}). Temperature, memory, free disk at \param{disk_path}, load
    per CPU, CPU busy share and Jetson GPU load, each against its limit (a limit of 0 turns the
    reading off; CPU and GPU are off by default). Thermal zones are read only when their type
    matches \param{system.thermal_zones} (CPU, GPU, junction, x86 package): some Jetson zones
    report bogus values (PMIC-Die at 100°C). Readings outside $-40$..150°C are ignored. A reading
    that cannot be obtained is a warning, never OK (review \#17).
\end{description}

Products add checks without forking: a \code{Check} subclass registered as an entry point in
the group \code{dharma_health.checks} and named in \param{extra_checks}
(Section~\ref{sec:plugin-example} shows the mechanism for a controller).

\textbf{Actionable output} (finding H1). The 0.1 monitor published JSON in a
\code{std_msgs/String} that nothing acted on. The report (\code{core/report.py}) takes the worst
level of all findings and the lowest speed scale any finding asks for: an error asks for 0, a
warning for the lowest matching \param{degradation.rules} entry (\code{<pattern>=<scale>},
fnmatch on the item name) or \param{warn_scale} (1). The defaults halve the speed while the LiDAR
or the estimator is slow or late, or a TF edge is late:
\code{sensor:/livox/lidar=0.5}, \code{sensor:/Odometry=0.5}, \code{tf:*=0.5}. The control mux
multiplies its commands by the scale when \param{use_health_limit} is set; a health status older
than \param{health_timeout_sec} (3~s) is ignored (scale 1). Health is a diagnostic aid, not a
safety function: the protective field and the e-stop never depend on it.

\section{TF latency budget}
\label{sec:tf-budget}

The follower looks up \frm{map}$\to$\frm{base_link} at the latest available time. tf2 returns the
transform at the \emph{latest common time} of the chain, the newest stamp available on every
edge, and the pose is stale when its age exceeds \param{safety.tf_timeout_sec} (0.5~s). With $E$
the dynamic edges, $\tau_e$ their stamps and $\Delta_e$ the clock offsets of their sources,
\begin{align}
  \mathrm{age}(t) &= t_{\mathrm{now}}^{\mathrm{consumer}} - \min_{e\in E}\tau_e,
    \qquad \tau_e = t_e^{\mathrm{measured}} + \Delta_e, \\
  \mathrm{age} &\approx \max_{e\in E}\Big(\underbrace{L_e^{\mathrm{acq}} + L_e^{\mathrm{proc}} +
    L_e^{\mathrm{tx}} + L_e^{\mathrm{queue}}}_{\text{latency}} - \Delta_e\Big) +
    \underbrace{\Delta_{\mathrm{consumer}}}_{\text{clock offset}} +
    \underbrace{(t_{\mathrm{now}} - t_{\mathrm{received}})}_{\text{publish period}}.
\end{align}
In Dharma two edges are dynamic: \frm{map}$\to$\frm{odom}, stamped with \code{now()} by
localization at 20~Hz (almost always fresh), and \frm{camera_init}$\to$\frm{body}, stamped by the
estimator with the end time of the LiDAR scan from the LiDAR's own clock. The LIO edge therefore
dominates:
\begin{center}
\begin{tabular}{@{}lr@{}}
  \toprule
  Contribution & Typical \\
  \midrule
  acquisition (one Mid-360 frame) & $\approx 100$~ms \\
  LIO processing & 20--80~ms \\
  DDS transport and queueing & a few ms, more under load \\
  until the next control tick & up to one period \\
  \midrule
  normal age & 0.15--0.35~s (limit 0.5~s) \\
  unsynchronized LiDAR clock & $+\Delta$, added directly \\
  \bottomrule
\end{tabular}
\end{center}

\subsection{Diagnosis in ten minutes}
\label{sec:ten-minutes}

\begin{enumerate}
  \item \textbf{Measure the sensor clock offset.} Print \code{header.stamp} of one
    \topic{/livox/lidar} message and compare it with the host clock at reception. A robust
    estimate is the median of $\hat\Delta = t_{\mathrm{received}} - \tau$ over 10~s; normally
    $\hat\Delta \approx 0.10$--$0.15$~s (acquisition and transport). Repeat for
    \topic{/livox/imu}, \topic{/Odometry} and the camera info.
  \item \textbf{Find the old edge.} \texttt{ros2 run tf2\_ros tf2\_monitor map base\_link} shows the
    average and maximum delay per edge. A large and stable delay of
    \frm{camera_init}$\to$\frm{body} points to T1; a fluctuating one to T3 or T4.
  \item \textbf{Check between machines.} \texttt{chronyc tracking}: the offset must be below 1~ms on
    a LAN.
  \item \textbf{Check the load.} \code{tegrastats}, \texttt{ros2 topic hz /tf},
    \texttt{ros2 topic bw /tf}.
  \item \textbf{Repeat standing still and driving.} A constant offset means a clock problem, an
    offset that grows while moving means load.
\end{enumerate}

\subsection{Fixes}

\textbf{In the system (T1, T2).}
\begin{itemize}
  \item PTP for the Mid-360: run \code{ptp4l} as master on the Jetson NIC connected to the LiDAR,
    with hardware timestamping when \texttt{ethtool -T} supports it, and \code{phc2sys} when the NIC
    clock must follow the system clock. The LiDAR stamps then share the host time base and
    FAST-LIO, perception and localization are consistent.
  \item Without PTP: restamp in the driver, $\tau' = t_{\mathrm{received}} - \hat L$ with the nominal
    latency $\hat L$ (scan duration plus transport), keeping the per-point time offsets for
    deskewing. Better than a free-running device clock, but its jitter enters the stamps.
    FAST-LIO's \code{time_sync_en} only aligns the LiDAR with the IMU, not with the host.
  \item Several computers: chrony with the Jetson as local server (or both on the same NTP server),
    \code{makestep} at boot, and the chrony check in health.
  \item Camera: make the driver use the host clock (RealSense: global time enabled), so the tag age
    limit and the odometry lookup at the tag stamp do not fail.
\end{itemize}

\textbf{In the stack (T3--T5)}, all in 0.2.0:
\begin{itemize}
  \item per-edge ages in \code{TfCache} and in health, so the message names the edge and the likely
    cause;
  \item stamp-age checks in health, not only rates;
  \item latency compensation in the follower: for ages between \param{safety.tf_compensate_sec}
    and the timeout the pose is predicted to the current time with the odometry twist,
    $\T{odom}{base}(t_{\mathrm{now}}) \approx \T{odom}{base}(\tau)\exp\big(\hat{\vect{\xi}}\,
    (t_{\mathrm{now}} - \tau)\big)$, and the robot stops only above the timeout;
  \item distinct states \code{TF_STARTING} (the gate holds), \code{TF_STALE} (age) and
    \code{TF_CLOCK} (a pose from the future), so an operator knows what to fix;
  \item no blocking service callbacks (L2), so \frm{map}$\to$\frm{odom} never pauses;
  \item a simulator that stamps with a latency, so regressions of T1 and T3 show in CI
    (Chapter~\ref{ch:sim}).
\end{itemize}
Reducing the \topic{/tf} load (joint states at most 30~Hz or on a separate topic; heavy Python
nodes reading \topic{localization/pose} instead of the whole \topic{/tf}) and real-time priority
with core isolation for the estimator help further.
